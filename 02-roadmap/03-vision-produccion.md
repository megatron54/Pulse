# Visión de producto: Pulse como app de producción (WHOOP/Garmin-like)

> Documento de trabajo vivo. Creado tras petición explícita del usuario de
> escalar Pulse de "app funcional" a "producto pulido, listo para vender".
> Esto es un proyecto de **meses**, no de una sesión — este documento existe
> para que cualquier sesión futura (mía o de otro agente) continúe
> exactamente donde se dejó, con criterio y evidencia, sin re-investigar
> lo ya investigado ni fingir progreso que no existe.

## Cómo se está operando este proyecto

- **No hay "cientos de agentes en paralelo corriendo indefinidamente"** de forma literal - eso no es técnicamente viable en una sesión de agente. Lo que sí se hace: delegar investigación/auditoría a subagentes especializados en paralelo cuando el trabajo es independiente (ya hecho: 4 investigaciones en paralelo para este documento), y ejecutar la construcción secuencialmente con TDD + revisión de código + verificación real (Playwright, curl, Docker) en cada pieza, igual que el resto del proyecto hasta ahora.
- **Comandos de shell largos o potencialmente colgados se lanzan en segundo plano, nunca bloqueando el turno del agente**: `C:\Users\migue\AppData\Local\Temp\opencode\bg-run.ps1` (lanza un comando detached, redirige stdout/stderr a log, guarda PID+exitcode), `bg-check.ps1` (comprueba estado sin bloquear - RUNNING/DONE/MISSING + cola del log), `bg-kill.ps1` (aborta un proceso que lleva demasiado tiempo colgado, para poder reportar honestamente en vez de esperar indefinidamente). Patrón: lanzar -> `Start-Sleep` corto -> comprobar -> repetir o abortar, nunca un único `timeout` largo bloqueando la respuesta.
- **Honestidad de progreso innegociable**: cada épica de este documento se marca como hecha solo cuando está verificada de verdad (tests pasando + build + revisión +, cuando aplica, prueba visual real). Nunca se declara "listo para producción" sin evidencia.
- **Reutilizar antes que reinventar** (petición explícita del usuario): antes de escribir una integración externa nueva, se investiga primero si wger (ya integrado) o el propio backend ya lo resuelven.

## Investigación ya realizada (no repetir)

### 1. Nutrición — wger ya resuelve esto, no añadir una tercera fuente
wger expone un módulo de nutrición completo en su API REST (ya usado por `wger_client/` para ejercicios):
- `ingredient/` / `ingredientinfo/` - catálogo de alimentos, en realidad datos de **Open Food Facts re-normalizados** (`source_name: "Open Food Facts"`). Público, sin auth, 120/min lista, 300/min detalle.
- `nutritionplan/` / `meal/` / `mealitem/` / `nutritiondiary/` - planes de dieta, comidas estructuradas, y el diario de consumo real (esto es exactamente el "food log" que falta).
- **Gotchas a programar defensivamente:**
  - Los campos numéricos de nutrientes vienen como **strings** (`"protein": "6.100"`) - castear a `Number` antes de sumar, si no, concatenación de strings silenciosa.
  - `fiber`/`is_vegan` suelen ser `null` (hereda la dispersión de datos de OFF) - nunca asumir presencia.
  - El orden de la lista de ingredientes **no está garantizado** - nunca asumir que `results[0]` es estable.
  - **CVE-2026-27839**: IDOR conocido en los sub-endpoints `.../nutritional_values/` de `nutritionplan`/`meal`/`mealitem` (filtra macros de otros usuarios vía PK secuencial). Confirmar que la instancia de wger usada está parcheada, o evitar esos sub-endpoints y calcular agregados en nuestro propio backend a partir de `mealitem`/`nutritiondiary` ya acotados al usuario autenticado.
- USDA FoodData Central y Open Food Facts directo: **descartados para v1** (más trabajo de integración por menos beneficio que reutilizar wger). Revisar solo si se necesita precisión de micronutrientes que wger/OFF no dan.

### 2. Garmin — actividades (carrera/ciclismo/fuerza) nunca se han sincronizado, solo recovery diario
El cliente actual (`garmin_sync/client.py`) solo trae HRV/training readiness/body battery/sueño - **nunca actividades**. Para añadir carrera/ciclismo/fuerza:
- Librería `python-garminconnect` (ya dependencia) expone `get_activities(start, limit)`, `get_activities_by_date(...)`, y detalle vía `get_activity_details`/`get_activity_exercise_sets` (este último es el que da series/reps/peso para fuerza).
- Forma del JSON de cada actividad: `activityType.typeKey` discrimina el deporte (`"running"`, `"cycling"`/`"road_biking"`, `"strength_training"`). Carrera trae `distance`, `avgStrideLength`, `steps`, `vO2MaxValue`. Ciclismo trae `averagePower`, `normalizedPower`, `trainingStressScore`. Fuerza no trae distancia/velocidad útiles - usar `get_activity_exercise_sets` para el desglose real.
- **Riesgo de bloqueo de cuenta**: el patrón peligroso NO es sondear `get_activities` con el token cacheado, es volver a hacer login repetidamente. Mantener la regla ya existente (un solo intento de login, token cacheado) y añadir: sondear la lista de actividades como mucho cada 15-60 min, y solo llamar a los endpoints de detalle (pesados) para IDs de actividad nuevos, nunca releer detalle de actividades ya vistas.
- Proyecto de referencia para inspiración de modelo de datos (no para reusar código directamente, es una app standalone con su propio stack InfluxDB): `arpanghosh8453/garmin-grafana`.

### 3. Fotos de progreso + composición corporal — NO calcular %grasa desde una foto
Investigación concluyente: MediaPipe Pose Landmarker (`@mediapipe/tasks-vision`, tarea `PoseLandmarker`) da 33 landmarks de pose en 2D/pseudo-3D, **no circunferencias corporales**. Sin profundidad real ni múltiples ángulos calibrados con objeto de referencia, un %grasa derivado de una sola foto **no es defendible** - violaría el principio ya aplicado en este proyecto de "nunca falsa precisión" (el propio método Navy con cinta métrica ya se cuida de esto mostrando siempre un rango, nunca un número puntual).
- **Plan v1 correcto**: capturar landmarks por foto (frontal/lateral/espalda, ya modelado en `ProgressPhoto.angulo`), mostrar solo una **tendencia relativa de silueta** (ratios hombro/cintura/cadera cambiando con el tiempo), etiquetada explícitamente como eso - nunca un número de %grasa.
- Un %grasa foto-derivado con rango (más ancho que el de la cinta métrica) solo como posible v2/experimental, exigiendo múltiples ángulos + objeto de referencia/altura conocida, y siempre contrastado contra el método Navy.
- Gotchas técnicas: todo cliente (`"use client"`, nunca SSR), servir los assets WASM/modelo desde `public/` propio (no CDN, por privacidad/CSP), modelo `full` (~9MB) cargado perezosamente solo al entrar al flujo de foto, nunca en el bundle principal.

### 5. MyFitnessPal — sin integración directa viable, wger sigue siendo la fuente principal
Petición explícita del usuario: conector a MyFitnessPal para importar el diario de comidas. Investigación honesta (no fabricar una promesa que no se puede cumplir):
- **La API pública de MyFitnessPal está cerrada desde ~2019** para terceros. Solo queda un programa de partners privado (contacto por email a `API@myfitnesspal.com`, sin auto-registro, sin documentación pública, sin SLA) reservado de facto a integraciones corporativas grandes (wellness de empresa). **No es viable para Pulse.**
- Librerías no oficiales (`python-myfitnesspal` y similares) hacen scraping de la web/app con cookies de sesión - MFP ha ido añadiendo CAPTCHA y rompiendo estos flujos activamente, y violan explícitamente sus Términos de Servicio. **Descartado para producción** (riesgo legal, de baneo de cuenta del usuario, y de rotura silenciosa en cualquier actualización de MFP).
- **Camino viable pero limitado**: MFP sincroniza de forma oficial y sancionada con **Apple HealthKit** (solo resúmenes diarios de calorías/macros, sin desglose por alimento, sin marca de tiempo, faltan cafeína y vitamina A) y de forma más débil con Google Health Connect (en transición, cobertura de nutrición no confirmada como robusta). Es decir: si Pulse en el futuro lee HealthKit por otros motivos (Garmin real, sueño, etc.), de paso podría leer estos resúmenes de MFP como dato **aproximado y secundario**, nunca como el diario estructurado principal.
- **Camino viable como herramienta puntual de migración**: MFP permite exportar el diario en CSV vía su función de exportación de datos (RGPD/CCPA) - útil como importación única de "trae tu histórico de MFP a Pulse" en el onboarding, nunca como sincronización continua (es manual, sin webhook, sin automatización).
- **Decisión**: no prometer "sincronización con MyFitnessPal" en el roadmap. wger (`nutritionplan`/`meal`/`nutritiondiary`, ya investigado en el punto 1) sigue siendo la única fuente estructurada real. HealthKit-como-fuente-secundaria y CSV-import-puntual son los dos únicos caminos honestos, y ambos son de prioridad baja/opcional.

### 6. Báscula de bioimpedancia (FeelFit) — mismo patrón: no perseguir la app concreta, apuntar a HealthKit/Health Connect
Petición explícita del usuario: conectar su báscula de bioimpedancia (app "FeelFit"). Investigación:
- FeelFit es una app de marca blanca (paquete Android `com.qingniu.feelfit`) de **Yolanda** (fabricante OEM chino de básculas Bluetooth), usada por decenas de marcas distintas de Amazon/AliExpress que en realidad son el mismo hardware/stack. No hay API pública ni documentación de desarrollador.
- Único acceso de terceros encontrado: `Sanji78/feelfit` en GitHub, un componente de Home Assistant que hace login con el email/contraseña reales del usuario contra la "nube" privada de Feelfit (no es una API oficial, es scraping de credenciales) - 5 estrellas, sin garantía de mantenimiento, se rompería sin aviso si Yolanda cambia su backend. **No es una base sólida para un producto.**
- No hay protocolo BLE (Bluetooth Low Energy) documentado públicamente para las básculas Yolanda/FeelFit (a diferencia de Xiaomi/Renpho, que sí tienen protocolos mapeados por la comunidad de `openScale`).
- **Camino viable**: FeelFit sí sincroniza de forma oficial con **Apple HealthKit**. El patrón correcto es el mismo que con MyFitnessPal - integrar genéricamente con HealthKit/Health Connect (de donde la mayoría de apps de básculas BIA - Renpho, Withings, eufy, Fitdays - también sincronizan), en vez de perseguir la nube privada de una marca concreta.
- **Verificado tras petición del usuario de investigar la conexión con Samsung Health**: la investigación secundaria inicial (fuentes web de terceros, incluida Sahha, una empresa agregadora de datos de salud) no encontró evidencia de que FeelFit escribiera a Health Connect en Android, y llegó a concluir explícitamente "no funciona en Android". **Esta conclusión ha sido corregida**: el usuario reporta de primera mano, usando la app FeelFit instalada en su propio dispositivo, que esta permite de forma nativa conectar con **Fitbit, Health Connect, Google Fit y Samsung Health**. Una observación directa del propio usuario sobre la app real es una fuente más fiable que blogs/webs de terceros que pueden estar desactualizados (FeelFit puede haber añadido esta integración después de la fecha de esas fuentes) - se toma esta información como el estado real vigente, y se descarta la conclusión anterior de "no viable en Android".
- **Implicación arquitectónica importante a documentar ahora, antes de prometer la funcionalidad**: Health Connect **no es una API en la nube** - es un almacén de datos de salud local, on-device, gestionado por Android, accesible únicamente vía el SDK nativo (`androidx.health.connect.client`) desde una app Android con los permisos concedidos por el usuario en ese mismo dispositivo. Pulse hoy es una aplicación web (Next.js) sin ningún componente nativo de Android - un navegador web **no puede leer Health Connect directamente**, no existe un endpoint REST ni un puente JavaScript oficial para ello. Para poder leer los datos de FeelFit vía Health Connect, Pulse necesitaría **añadir un componente Android real** (app nativa mínima, o un wrapper tipo Capacitor/Expo alrededor del frontend web actual) cuya única función sea: pedir permisos de lectura de los registros de Health Connect relevantes, leerlos, y enviarlos al backend de Pulse vía la API REST ya existente. Esto es una expansión de plataforma real (Pulse pasa de "solo web" a "web + app Android"), no una integración trivial - debe planificarse y estimarse como tal, no prometerse como si fuera "conectar un webhook".
- **Tipos de registro de Health Connect a leer** (confirmados como parte de la plataforma, con nombres reales de la API): `WeightRecord`, `BodyFatRecord`, `BasalMetabolicRateRecord`, `BoneMassRecord`, `LeanBodyMassRecord`, `BodyWaterMassRecord`. Permisos Android correspondientes: `android.permission.health.READ_WEIGHT`, `READ_BODY_FAT`, `READ_BASAL_METABOLIC_RATE`, `READ_BONE_MASS`, `READ_LEAN_BODY_MASS` (y equivalente para agua corporal). Publicar esto en Google Play requiere declarar el uso de "permisos sensibles de salud" y pasar la revisión correspondiente de Google.
- **Plan de implementación concreto** (Épica nueva, ver tabla de épicas): (1) decidir el shell técnico de la futura app Android (nativo Kotlin mínimo vs. Capacitor sobre el frontend Next.js ya existente - preferible Capacitor para reutilizar la mayor parte del código ya construido y no duplicar UI), (2) módulo nativo/plugin que solicite permisos de Health Connect y lea los `Record` relevantes, (3) endpoint nuevo en el backend (`POST /users/{id}/body-composition/external-import` o similar) que reciba estos valores y los persista, marcados explícitamente con su origen (`metodo="bioimpedance_healthconnect"`, no `"navy"` ni `"manual"`, para que nunca se confundan en la UI ni en el histórico), (4) aplicar el hallazgo de honestidad de datos de abajo en cómo se presenta este dato frente al rango de la cinta métrica.
- Único acceso de terceros a la nube privada de Feelfit sin pasar por Health Connect (`Sanji78/feelfit` en GitHub, scraping de credenciales, sin garantía de mantenimiento) sigue descartado como base de un producto - con la vía de Health Connect confirmada como real, no hace falta ese atajo frágil.
- **Hallazgo crítico de honestidad de datos** (coherente con el principio ya aplicado de "nunca falsa precisión"): la bioimpedancia de consumo tiene un error real de **±3-8% de grasa corporal frente a DEXA**, igual o peor que el método Navy de cinta métrica (±3-4%), y con una fuente de error adicional que la cinta no tiene - la hidratación (una variación del 2% en agua corporal puede desplazar la lectura 3-4 puntos porcentuales en una misma sesión). **Un valor de bioimpedancia NUNCA debe promediarse con el rango de la cinta métrica como si fuera una medición independiente igual de fiable** - los dos métodos no son fuentes de error independientes y la bioimpedancia no es más precisa. Si algún día se integra, debe mostrarse como una señal secundaria de **tendencia** (¿la pendiente coincide con la del rango de cinta a lo largo de semanas?), con su propio rango más ancho, etiquetada explícitamente como "sensible a la hidratación, menos fiable día a día" - nunca como un valor que estrecha o sustituye el rango de la cinta.
- **Preferencia explícita del usuario (aclarada tras este análisis)**: el usuario confirma que ya tiene FeelFit Y Samsung Health conectados en su propio teléfono. Prioridad: (1) conectar FeelFit directamente si resulta viable - trae el dato más crudo/directo, sin la capa de agregación de Samsung Health de por medio; (2) si FeelFit resulta demasiado difícil de integrar en la práctica, Samsung Health es el plan B aceptable (ambos pasan por el mismo mecanismo real: Health Connect en Android, ver más abajo - la app Android que Pulse necesita construir para leer Health Connect es la misma pieza de infraestructura sirva para leer FeelFit o Samsung Health, así que esta decisión no cambia el plan de implementación, solo qué tipos de `Record` se leen primero).
- **Confirmación independiente + prior art encontrado** (hilo de Reddit r/Garmin, "App for syncing weight from android health connect to garmin connect", may 2026): un usuario con la MISMA app (FeelFit) confirma independientemente que sincroniza a Health Connect, reforzando el hallazgo de más arriba. Dato nuevo relevante: **Garmin Connect NO importa peso desde Health Connect** (solo exporta algunos datos hacia allí) - irrelevante para Pulse en sí (Pulse no necesita pasar por Garmin Connect para esto, lee Health Connect directamente), pero confirma que Health Connect es un almacén neutral, no algo que Garmin ya resuelva por su cuenta. Más útil: dos repos open-source de referencia para la futura app Android de Pulse que lea Health Connect - `gsaw0/hc2garmin` (Android, permisos de lectura de peso/%grasa desde Health Connect, construida con ayuda de IA por el propio autor) y `Jacopo1891/fit2garmin` (su base de referencia) - sirven como ejemplo real de código Android que ya resuelve "pedir permiso y leer un `WeightRecord`/`BodyFatRecord` de Health Connect", el mismo primer paso que necesita el plan de implementación de arriba (punto 2). No para reusar directamente (su objetivo final es subir a Garmin, no a nuestro backend), sí como referencia de la parte de lectura de Health Connect.

### 7. Visión completa de nutrición pedida por el usuario — qué ya existe, qué falta, y cómo encaja todo
El usuario pidió que la página de Nutrición sea equivalente a MyFitnessPal: calculadora de calorías (cut/mantenimiento/surplus), manejo de macros, recetas, input diario, y una capa de IA que combine nutrición + entrenamiento (Garmin) + sueño + fotos de progreso + peso + %grasa para proponer ajustes (ayuno intermitente, ventanas horarias, redistribución de macros/micros). Desglose honesto de qué ya existe y qué es trabajo nuevo:

| Pieza pedida | Estado |
|---|---|
| Calculadora de calorías cut/mantenimiento/surplus | ✅ Ya existe (`engine/nutrition.py`, Capa 1, determinista) - falta exponerlo con más detalle en la UI (hoy solo se ve el resultado final del día) |
| Manejo de carbohidratos/grasa/proteína | ✅ Ya existe (mismo motor) |

| Recetas | ⬜ Falta por completo - wger no tiene un módulo de "recetas" propiamente (solo ingredientes sueltos) - requiere modelo de datos nuevo en Pulse (una receta = lista de `mealitem` + instrucciones), evaluar si merece la pena vs. simplemente permitir guardar una combinación de `mealitem` como plantilla reusable dentro de wger's `meal` |
| Conector MyFitnessPal | ❌ No viable como sync en vivo (ver punto 5) - solo HealthKit-secundario o CSV-import puntual, ambos de prioridad baja |
| Báscula de bioimpedancia (FeelFit) | ✅ Viable vía Health Connect (confirmado por observación directa del usuario, ver punto 6) - requiere una app Android nueva (Capacitor), no es solo backend/frontend web; salvaguarda de honestidad de datos obligatoria en cómo se presenta frente al rango de la cinta métrica |
| IA que combina nutrición+entrenamiento+sueño+fotos+peso para proponer ajustes | ⬜ Falta por completo - es la pieza más grande y más delicada de todo el backlog, ver análisis abajo |

**Sobre la capa de IA de ajuste de dieta (la pieza más grande y más delicada):**
Esto no es "una llamada más a Gemini" - es un motor de decisión con implicaciones de seguridad (recomendar ayuno intermitente o redistribuir calorías según hora del día a alguien con mala recuperación sostenida, o basándose en fotos de progreso, es un consejo de salud). Coherente con la arquitectura de 3 capas ya establecida en este proyecto (Capa 1 determinista decide, Capa 3/IA solo explica - nunca al revés), esto NO puede construirse como "la IA decide qué cambiar en tu dieta". El camino correcto:
1. **Capa 1 nueva (determinista, sin red)**: un motor de reglas explícito para las variaciones de timing/ayuno intermitente/redistribución de macros, con umbrales y condiciones auditables (igual que `engine/periodization.py` y `engine/guardrails.py`) - por ejemplo: "si la recuperación lleva 3+ días en amarillo/rojo Y el usuario está en déficit, sugerir redistribuir carbohidratos hacia el entrenamiento en vez de ayuno prolongado" son reglas que se pueden y se deben codificar explícitamente, no delegar a un LLM que "decide".
2. **Inputs reales que ya existen o están en construcción**: recovery (✅), carga de entrenamiento numérica (✅, recién construida), sueño (parcialmente, dentro de Garmin daily metrics, bloqueado por Fase H), peso/%grasa (✅), fotos de progreso (⬜ Fase G, y recordar: solo tendencia de silueta, nunca %grasa por foto).
3. **Capa 3 (IA/Gemini)**: como en el resto del proyecto, solo redacta la explicación de una decisión que la Capa 1 ya tomó con datos reales - nunca inventa un plan de ayuno intermitente por su cuenta ni tiene la última palabra.
4. Este motor de reglas necesita su propia investigación de literatura científica (igual que se hizo para periodización, ver `00-research/06-periodizacion-ciencia-deportiva.md`) antes de codificar ningún umbral - el ayuno intermitente y el timing de nutrientes son áreas con evidencia mixta/contestada, así que cualquier regla debe documentar su fuente y ser conservadora (nunca forzar una restricción horaria a alguien sin evidencia sólida de beneficio, y siempre permitir override manual del usuario).

**Este documento NO promete fecha para esta capa de IA** - es, con diferencia, la pieza de mayor riesgo y mayor esfuerzo de todo el roadmap, y requiere su propia sesión de investigación dedicada antes de estimarla con seriedad.

### 8. Diario de hábitos (PR #37) — hallazgo de diseño: la ausencia de fila no basta como "grupo de control" estadístico
Al construir la Épica 7, code-review encontró un CRITICAL que vale la pena documentar para no repetirlo en features futuras con la misma forma: `HabitLog` usa "presencia de fila = ocurrió, ausencia = no ocurrió" (append-only). Eso es correcto para saber SI un hábito ocurrió un día concreto, pero **no basta** para construir el grupo de comparación "días en los que NO ocurrió" de un análisis de correlación - un día sin fila es indistinguible de "el usuario nunca hizo check-in ese día" y de "confirmó explícitamente que no pasó nada". Se resolvió añadiendo una tabla separada `HabitCheckin(user_id, fecha)` que registra SIEMPRE que hubo check-in (se marcara algo o no); el grupo de control se restringe a esas fechas, nunca al calendario completo. **Regla general para el futuro**: cualquier tabla con semántica "ausencia = señal negativa" que además vaya a usarse para comparar contra un grupo de control necesita una tabla/columna adicional que registre "hubo intento de registro" - la sola ausencia de una fila de evento nunca es suficiente evidencia de un evento negativo confirmado.

### 9. Ingestión de actividades Garmin (PR #38) — nombres de campo reales confirmados contra el código fuente
Al construir la Épica 2 se confirmaron (leyendo `garminconnect/typed.py` en `recursos/repos/python-garminconnect/`, no solo inferidos) los nombres de campo reales de `get_activities_by_date`: `activityId`, `startTimeLocal` (formato `"YYYY-MM-DD HH:MM:SS"`, hora local, sin TZ), `activityType.typeKey`, `duration`/`averageHR`/`maxHR` (todos **float**, no int - hay que redondear, `int()` trunca y sesga sistemáticamente a la baja), `distance` (metros), `aerobicTrainingEffect`, y para fuerza `totalSets`/`totalReps`/`totalVolume` (sin usar todavía - candidatos para una futura vista de detalle por sesión, Épica MUST-HAVE #2). La idempotencia de la ingesta (`(user_id, activity_id)` como clave real de deduplicación) se protegió con un `UniqueConstraint` en el modelo, no solo con una comprobación en código - mismo criterio que motivó `HabitCheckin` en el punto 8: cualquier invariante de "no duplicar"/"no repetir" debe estar respaldada por la base de datos, un `if` en Python nunca es suficiente si existe la más mínima posibilidad de concurrencia futura.

### 10. Resumen periódico (PR #40) — los repositorios de historial NO comparten el mismo criterio de ventana entre sí
Al agregar tres repositorios distintos (`get_readiness_history`, `get_weight_history`, `get_activity_history`) en un mismo servicio, code-review encontró que **no todos usan la misma convención de límites**: los dos primeros devuelven `days+1` días (`as_of - timedelta(days=days)` con límites inclusivos por ambos lados - el mismo off-by-one que ya se había corregido una vez en `get_volumen_pct_history`, pero que sigue sin corregirse en estos otros dos), mientras que `get_activity_history` ya usa el criterio correcto (`days` exactos, `as_of - timedelta(days=days-1)`). Se resolvió filtrando explícitamente la ventana en la capa de servicio (`periodic_summary_service.py`) en vez de tocar los repositorios compartidos (para no arriesgar otros consumidores que puedan depender implícitamente del comportamiento actual). **Deuda técnica pendiente, explícita**: `get_readiness_history` y `get_weight_history` deberían corregirse igual que se corrigió `get_volumen_pct_history`, y sus consumidores existentes (`ReadinessTrendCard`/`WeightTrendCard` u otros) deberían auditarse para confirmar que no dependen del `+1` día de más. **Regla general para el futuro**: al construir cualquier función que agregue sobre múltiples repositorios de historial con parámetro `days`, verificar explícitamente que todos usan el mismo criterio de ventana antes de asumirlo - no dar por sentado que "días" significa lo mismo en cada repositorio del proyecto.

### 11. Scheduler containerizado (PR #47) — el token OAuth de Garmin no puede vivir en una ruta del host
El job nocturno (`scheduler/app.py`) solo podía correr manualmente (`python -m scheduler.app` en un terminal dejado abierto), lo cual es incompatible con el objetivo de "arrancar todo con un solo comando". Al añadir el cuarto servicio (`scheduler`) a `docker-compose.yml` reutilizando la imagen de `backend`, apareció un problema real: el token OAuth cacheado de Garmin (`GarminCredentials.token_store_dir`) apuntaba a una ruta del host Windows (`C:\Users\<usuario>\.garminconnect\...`), invisible desde un contenedor Linux. **Solución**: un volumen Docker nombrado (`garmin-tokens`) compartido entre `backend` y `scheduler`, montado en `/data/garmin-tokens`; `scripts/garmin_pair.py` ahora lee el directorio base vía `PULSE_GARMIN_TOKENS_DIR` (con fallback a `~/.garminconnect` para local sin Docker), refactorizado a función en vez de constante de módulo (evita que los tests necesiten `importlib.reload`, que dejaba el valor cacheado filtrado entre tests si alguno olvidaba recargar de vuelta - hallazgo de @code-reviewer). Migración manual de los datos reales (perfil, credenciales, métricas) desde el volumen Postgres de un proyecto compose anterior al nuevo, vía `pg_dump`/`psql`, sin pérdida. **Hallazgo secundario**: el `HEALTHCHECK` heredado del Dockerfile de `backend` asume un servidor HTTP en `:8000/health`, pero `scheduler` no expone puerto - se sobrescribió con un healthcheck de liveness de proceso (`grep` sobre `/proc/*/cmdline`, ya que `python:3.12-slim` no trae `pgrep`) en vez de deshabilitarlo del todo, para no perder toda señal de vida si el proceso muriera. Verificado end-to-end: sync real ejecutado dentro del contenedor (`SyncBatchResult(exitosos=1, fallidos=0)`), datos nuevos del día (`sleep_score`, `hrv_value`, `body_battery_am`) ya en la BD.

### 12. intervals.icu — única vía gratuita confirmada para ESCRIBIR entrenamientos de vuelta al reloj (investigación preliminar, sin implementar)
El usuario compartió el hallazgo de que **intervals.icu** ofrece un programa "Build Your Own Coach" gratuito. Relevancia: Pulse hoy **solo LEE** de Garmin (recovery, actividades) - nunca escribe nada de vuelta al dispositivo. Un constructor de entrenamientos estructurados que empuje sesiones al reloj (ya listado como SHOULD-HAVE en el punto 4) requeriría o bien la API oficial de Garmin Connect (de pago/partner, no confirmada como accesible para un desarrollador individual) o un intermediario como intervals.icu, que sí sincroniza en ambas direcciones con Garmin Connect de forma gratuita para cuentas individuales.
- **No investigado todavía en profundidad**: términos de uso exactos de la API de intervals.icu, límites de rate, si requiere que el usuario tenga una cuenta intervals.icu además de la de Garmin (probablemente sí), y si el "Build Your Own Coach" es literalmente una API pública documentada o un producto de coaching cerrado. **Antes de prometer esta integración, hace falta una sesión de investigación dedicada** (mismo patrón que se exige para cualquier integración externa nueva en este documento) - no se ha verificado nada de esto contra fuentes primarias todavía, solo se registra la pista para no perderla.
- **Patrón relacionado mencionado por el usuario, también sin implementar**: un archivo `coach.md` (preferencias de coaching persistentes y editables directamente por el usuario en texto plano) que condicione el tono/énfasis de la Capa 3 (explicación conversacional) sin que la IA decida nada nuevo por su cuenta - coherente con el principio ya establecido de "la IA nunca decide, solo explica"; el archivo sería un input más a la plantilla de explicación, no una fuente de reglas nuevas.
- **Canal de entrega adicional mencionado, también sin implementar**: Telegram como canal alternativo/complementario al frontend web para recibir el resumen narrativo de la Capa 3 (ej. mensaje diario con el resumen de recovery/plan del día). Requeriría un bot de Telegram propio (token de `@BotFather`, nunca compartido en un chat de IA, mismo principio que credenciales de Garmin/wger) y un endpoint/job que empuje el mensaje ya generado por la Capa 3 - no un chat conversacional nuevo dentro de Telegram (ya descartado explícitamente como WON'T-HAVE-YET en el punto 4).
- **Decisión**: dado el effort budget de la sesión, se documenta como research para retomar más adelante - no se ha implementado nada de esto todavía. No añadir a la tabla de épicas hasta tener la investigación dedicada de intervals.icu (términos, límites, viabilidad real de escritura).

## Principios que no cambian con la escala del proyecto

- TDD real, revisión de código antes de cada merge, verificación honesta (no fingir que algo funciona sin probarlo).
- Nunca falsa precisión: rangos donde el dominio es incierto, categorías donde el motor de reglas es categórico. Esto aplica igual a bioimpedancia que a fotos: un método que no es más preciso que el que ya usamos no debe presentarse como si lo fuera.
- Reutilizar wger antes que añadir una integración externa nueva - y cuando ni siquiera wger sirve (MyFitnessPal, FeelFit), decir honestamente que no hay integración viable en vez de prometerla.
- La IA (Capa 3) nunca decide, solo explica una decisión ya tomada por reglas deterministas auditables (Capa 1) - esto se aplica también a cualquier futura sugerencia de dieta/ayuno/timing, sin excepción.
- Documentar cada decisión y hallazgo aquí, para que la siguiente sesión no repita la investigación.
